寫 TypeScript 時最常見的挫折是：程式明明能跑，編譯器卻不讓你過。
於是產生兩種反應——加上 `as any`，或者花二十分鐘拼湊一個複雜的泛型。
兩種都把型別當成了關卡。

## 型別回答的是設計問題

考慮一個資料載入狀態。多數人的第一版會這樣寫：

```ts
interface State {
  loading: boolean;
  data?: User[];
  error?: Error;
}
```

這個型別是合法的，但它允許 8 種組合，其中有 5 種在現實中不可能發生——
例如 `loading: true` 同時 `error` 有值，或者 `data` 與 `error` 同時存在。

問題不在於編譯器太嚴格，而在於這個型別描述的世界比真實世界大。
每一個不可能的組合，最後都會變成某處的一行防禦性判斷。

### 讓不可能的狀態無法被表達

```ts
type State =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: User[] }
  | { status: "error"; error: Error };
```

現在只剩 4 種狀態，而且每一種都攜帶且僅攜帶它需要的資料。
`status === "success"` 之後 `data` 必定存在，這不是約定，是型別保證。

這個改動沒有用到任何進階語法。它用的是**思考**，不是**技巧**。

## 兩個判斷準則

當你不確定一個型別設計得好不好，可以問這兩個問題：

1. 這個型別允許的組合中，有多少是現實中不可能的？
2. 如果有人寫出了那些不可能的組合，會在什麼時候被發現？

第一個問題衡量型別的精確度，第二個問題衡量錯誤的成本。
好的型別設計會把答案分別推向「零」與「編譯期」。

## 什麼時候該停下來

型別可以無限精確下去，但收益會遞減。
一個實用的停損點是：**當型別的複雜度開始超過它所保護的邏輯時，就該停了。**

如果你為了驗證一個字串是合法的 email 而寫了 40 行 template literal type，
那 40 行本身就成了新的維護負擔，而執行期驗證只需要 3 行。

型別擅長處理結構，不擅長處理值。認清這條界線，比學會任何一個進階技巧都有用。
