# ADR 0008：建立效能預算閘門

- 狀態：已接受
- 日期：2026-07-27

## 脈絡

本專案有一條貫穿全域的鐵則：

> 所有 editor 與重量級互動元件一律不得進入初始載入路徑。

問題在於：**「按需載入」不是一次性決策，而是每次新增元件都可能悄悄破壞的性質。**

典型的失效路徑：某個元件為了共用一個小工具函式而 import 了 editor 模組的 barrel file，Rollup 因此把整個 editor 拉進共用 chunk。這類退化沒有任何錯誤訊息，只有在有人主動檢查產物時才會發現。

若等到第 8 個互動元件才發現退化，回頭拆解的成本極高 —— 屆時已無法判斷是哪一次變更引入的問題。

## 決策

**在基礎建設階段（新增任何互動元件之前）就建立自動化的效能預算閘門。**

實作為 build 後執行的檢查腳本（約十幾行 Node），對 `dist/` 產物驗證：

1. **Global / 共用 chunk 的 JS 總量上限** —— 核心防線，確保重量級依賴未洩漏進共用路徑
2. **單一 chunk 體積上限** —— 偵測意外的依賴合併
3. **每頁初始載入的 JS 總量** —— 純文章頁應趨近於零
4. **字型與靜態資源總量** —— 涵蓋 [ADR 0004](0004-cjk-font-strategy.md) 的風險

超過紅線即 build 失敗。

### 補充決策：紅線分為「人人都付」與「按需才付」兩類（2026-07-28）

上列四條隱含一個假設：所有產物都在初始載入路徑上。階段六的 Pagefind 打破了它 ——
執行期 151KB 只在讀者第一次打開搜尋時才 import，把它算進 `singleChunk` 會讓
「最大單一 chunk」永遠指向 `pagefind.js`，那條檢查就再也回答不了它唯一該回答的問題
（我們自己的程式碼有沒有意外合併）。當時的處理是排除它、另開 `searchRuntime` 一條。

**那次處理是對的，但它當時只是一個特例。** 階段九的 GSAP 與階段十的 CodeMirror
（~200KB）會再遇到完全相同的情境，而臨時決定在壓力下的預設答案就是調高紅線。
因此把它升格為規則：

| 類別 | 語意 | 現有紅線 | 撞線的正確反應 |
|---|---|---|---|
| **人人都付** | 位在初始載入路徑上，每個讀者無條件付費 | `sharedJs`、`pageInitialJs`、`singleChunk`、`cssCacheable`、`pageInlineCss`、`staticAssets` | 修正架構。調高需在 commit message 說明理由 |
| **按需才付** | 執行期 dynamic import，只有觸發該功能的讀者才付 | `searchRuntime`、`searchIndex`（未來：`editorRuntime` 等） | **先確認它真的還是按需的**，確認後才談數字 |

兩件事必須明確：

1. **按需類的產物一律排除於「人人都付」各條之外**，否則它們會淹沒那些檢查的訊號。
   排除本身不是放寬 —— 每一項排除都必須同時開一條屬於自己的紅線，沒有產物可以因為
   「不屬於任何一條」而消失在報告裡。
2. **按需類撞線時，第一個要問的不是「該調高嗎」而是「它還是按需的嗎」。**
   CodeMirror 撞 `sharedJs` 是退化（island 邊界破了），撞它自己的 `editorRuntime`
   多半只是套件變大 —— 兩者的正確反應完全相反，混在一條紅線裡就分不出來。

換句話說：這些檢查的目的從來不是「總量要小」，而是**讓每一筆成本能被歸因到付它的人**。

### 補充決策：底網，以及「初始載入」的可觀測定義（2026-07-28，階段八）

上面第 1 點要求「每一項排除都必須同時開一條屬於自己的紅線」。階段八實作第一個延後載入的
元件時發現，那條規則的執行方式是**人要記得** —— 而忘記的下場不是報錯，是那筆體積永遠不會
失敗。這與本 ADR 想消滅的失效模式是同一個，只是換了位置。因此補兩件事：

1. **底網（`deferredIslands`）**：一條涵蓋「所有沒有人在初始載入時抓的自有 JS」的紅線。
   新元件即使忘記開專屬紅線也不會消失 —— 它會自動落進底網；大型套件另開專屬紅線之後，
   再從底網扣除。規則從「記得開一條」變成「預設就有一條」。

2. **「初始載入」必須用可觀測的性質定義，而且要跟著靜態 import 圖走**：
   HTML 沒有引用它，**且**它不在任何被引用 chunk 的靜態 import 圖上。

   第二個條件是實測撞出來的。閘門原本只認 HTML 裡寫出來的檔名，而 Rollup 會把多個
   動態 import 點共用的 Vite preload helper 抽成獨立 chunk —— 那支 chunk 只被 entry chunk
   以 `import` 敘述引用，HTML 裡沒有它的名字。於是階段八新增第二個動態 import 點時，
   1394 B 從「人人都付」憑空消失，閘門把共用 JS 從 6.9 KB 報成 **6.0 KB**：
   初始 JS 實際增加約 500 B，報告卻說減少 900 B。

   這是第三次同一形狀的事故（階段六的 CSS 量錯對象、階段六補的量錯目錄、這次的漏算
   import 圖），三次的共同點都是**閘門說的話比它知道的多**。因此判準改為與鐵則
   逐字對應的那句話，而不是「HTML 裡有沒有出現」這種實作上的近似。

## 理由

- 讓「按需載入」從**人工紀律**變成**機器保障**。前者必然隨時間鬆弛。
- 提供即時回饋：加入 CodeMirror、Monaco、GSAP 時能立刻看到代價，使取捨基於數字而非直覺。
- 定位在建置順序的第 4 步（基礎三件套完成後、任何互動元件之前），因為此時的產物最乾淨，是設定基準線的最佳時機。

## 後果

- 需維護一份紅線設定，並在有正當理由時調整（調整應是有意識的決定，而非隨手放寬）。
- 早期會有少量誤報，需花時間校準閾值。
- 增加一個 build 步驟。

## 使用原則

- **紅線調高必須附理由**，記錄於 commit message。若某次調整無法說明，代表該次變更本身需要重新檢視。
- 閘門失敗的預設反應是**修正架構**，而非放寬閾值。
- Monaco 引入時（[ADR 0006](0006-editor-codemirror.md)）需特別驗證：兩套 editor engine 確實分屬不同 chunk，未被合併。
- 新增「按需才付」的產物時，**必須同時開一條屬於它的紅線**。只排除不設限等於讓那筆體積從報告裡消失，
  比計錯位置更糟 —— 階段六補的教訓是「失敗看起來跟成功一樣」，沒有數字的產物永遠不會失敗。
  （階段八起有底網接著，忘記開紅線不會再讓體積消失；但底網是安全網而非替代品 ——
  大型套件仍應各自開紅線，否則「我們自己的按需元件有多大」這個訊號會被淹掉。）
- **閘門自己也會壞，而且壞得沒有聲音。** 已發生三次：量錯對象（階段六的 CSS 總量）、
  量錯目錄（階段六補的 `dist/client`）、漏跟 import 圖（階段八的 preload helper）。
  因此新增或修改檢查時，除了「它會不會誤報」，必須一併問**「它讀不到東西時會說什麼」**——
  三次事故的共同症狀都是綠燈與一個看起來很正常的數字。

## 已評估的替代方案

| 方案 | 否決理由 |
|---|---|
| 人工定期檢查 `dist/` | 必然隨時間鬆弛，且退化發現時已難以定位來源 |
| Lighthouse CI | 量測的是綜合體驗分數，對「哪個依賴洩漏進共用 chunk」這個具體問題定位能力弱；可作為後期補充而非核心閘門 |
| `rollup-plugin-visualizer` | 優秀的**診斷**工具（閘門失敗後用它定位），但它只產生報告、不阻斷 build，無法作為保障機制 |
| 等有問題再處理 | 正是本 ADR 要避免的失效模式 |
