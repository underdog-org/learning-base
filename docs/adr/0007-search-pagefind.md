# ADR 0007：搜尋採用 Pagefind

- 狀態：已接受
- 日期：2026-07-27

## 脈絡

[ADR 0001](0001-self-built-astro-docs.md) 選擇自建 Astro 文檔站，因此需自行補上搜尋功能。

本專案的搜尋有一個特殊需求：**內容以中文為主**。中文沒有空格分詞，多數為拉丁文設計的全文搜尋方案在中文上的召回率極差。

## 決策

採用 **Pagefind**。

- Build 期掃描產出的靜態 HTML，生成分片索引
- 執行期按需載入索引分片，不需後端服務
- **原生支援中日韓分詞**
- UI 層：先自建（消費 Pagefind 的 JS API），不使用 `@pagefind/default-ui`

## 理由

- CJK 分詞是決定性因素。Pagefind 對此有第一級支援，而 Lunr / FlexSearch 等方案需額外掛分詞器且效果不穩。
- 靜態索引與本專案的部署形態（純靜態站）天然契合，無需維護搜尋服務或申請外部服務額度。
- 索引分片化，搜尋成本與站點規模解耦，符合專案的按需載入原則。
- UI 自建而非用 `@pagefind/default-ui`：後者帶有自己的樣式，與 [ADR 0002](0002-style-system-tokens-cjk.md) 的 token 體系衝突，且搜尋框是使用者高頻接觸的元件，值得自己控制。

## 後果

- 索引在 build 期生成，內容更新需重新 build 才會反映在搜尋結果中（對靜態知識庫可接受）。
- 需在 build pipeline 中加入 Pagefind 步驟（在 `astro build` 之後對 `dist/` 執行）。
- 搜尋 UI（輸入框、結果列表、鍵盤導航、快捷鍵）需自行實作，約一個 Web Component 的工作量。
- 搜尋元件同樣受鐵則約束：Pagefind 執行期不得進入初始載入路徑，只在使用者觸發時以
  執行期 `import()` 載入（實作見 `SiteSearch.astro`，那也是本專案第一個這種形狀的元件）。

## 中文召回率實測（2026-07-28，9 頁 / 784 詞）

決策當時「Pagefind 原生支援 CJK 分詞」是引用文件而非實測。階段六在寫任何 UI 之前先驗了這件事，結論是**決策成立，但 UI 必須為兩個實測出來的性質而設計**。

驗證方式：`astro preview` + 直接呼叫 Pagefind JS API，18 個查詢，每個查詢的期望值來自對 `src/content` 的 grep 而非印象。

**召回（recall）—— 沒有問題。** 二字詞、四字複合詞、六字長詞（`額外屬性檢查`）、含未必成詞尾巴的長查詢（`結構型別的相容性`）、中英混合查詢（`GSAP 動畫`）、駝峰式技術詞（`ScrollTrigger`）全部命中且正確的頁面排第一。`lang="zh-Hant"` 已足夠，**不需要 `--force-language zh`** —— 兩者索引出的詞數完全相同（784），`zh-Hant` 與 `zh` 走的是同一個分詞器。

**`pagefind-entry.json` 中 `"wasm": null` 是正常的。** CJK 沒有詞根，分詞在建置期由 Rust CLI 完成，wasm 只負責詞幹還原，因此 CJK 語言會落到 `wasm.unknown.pagefind`。建置時的 `Pagefind doesn't support stemming for the language zh-hant` 是預期訊息，不是退化警告。

**精確度（precision）有一個結構性的洞，且無法用分數門檻解決。** Pagefind 對查詢的最後一個詞做前綴比對，中文的單字因此會比對到大量詞彙：

| 查詢 | 站上存在 | 實得 | 成因 |
|---|---|---|---|
| `量子力學` | 否 | 1 筆 | 「量」前綴比對到「字面量」 |
| `中文排版` | 否 | 2 筆 | 「中」「文」散布全站 |
| `咖啡拿鐵` | 否 | 0 筆 | 不共用任何字，正確落空 |
| `結構 型別` | 是 | 0 筆 | 空白分隔為 AND，而非末詞的 `結構` 需精確成詞 |

分數無法區分訊號與雜訊：雜訊 `量子力學` 得 2.74，而真實命中 `額外屬性檢查` 只得 1.18。**跨查詢的分數門檻行不通**，此路已封。

因此搜尋 UI 的設計約束：

- **排序即是唯一的品質保證**，UI 不能暗示「有結果就是相關」。摘要片段（`excerpt`）必須顯示 `<mark>`，讓讀者一眼看出為何命中。
- **少於 2 個字元不觸發搜尋** —— 單字查詢（`中` → 4 筆、`的` → 9 筆）必然是雜訊。
- **不要向使用者暴露空白分隔的 AND 語法**，它在中文下的行為違反直覺。引號精確片語則正常（`"結構型別"` 命中、`"型別結構"` 落空）。

## 產物與預算

Pagefind CLI **沒有「只產索引、不產 UI」的選項**，一律寫出三套預設 UI 與 highlight 腳本（234KB JS + 63KB CSS）。本 ADR 決定自建 UI，這些檔案沒有任何頁面引用，但會一起被部署 —— 由 `scripts/prune-search-bundle.mjs` 在索引之後刪除。

階段四的閘門（ADR [0008](0008-performance-budget-gate.md)）因此新增兩條，並將 `dist/pagefind/` 排除於 `singleChunk` 之外（否則「最大單一 chunk」永遠指向 45KB 的 `pagefind.js`，那條檢查就答不了「我們自己的程式碼有沒有意外合併」）：

- `searchRuntime` 155009 B —— 固定成本，作用是回歸測試：刪除清單一旦失準，這裡立刻多出 200KB 以上（已實測，會報 497.5 KB）
- `searchIndex` 21536 B / 9 頁 —— **全站唯一隨內容線性成長的產物**，約每頁 2.4KB

搜尋元件本身的 JS 為 4.2KB，進共用 bundle（12 頁共用一支）。這不違反「重量級互動元件永遠不進 global bundle」的鐵則 —— 進 bundle 的只有那顆按鈕與對話框的邏輯，Pagefind 的 176KB 執行期走使用者觸發時的 dynamic import，沒打開搜尋的讀者一個位元組都不付。

## 已評估的替代方案

| 方案 | 否決理由 |
|---|---|
| Algolia DocSearch | 免費方案需申請與審核、依賴外部服務、CJK 分詞需額外設定，且索引更新受爬蟲排程限制 |
| Lunr.js / FlexSearch | 需自行處理 CJK 分詞，索引為單一大檔（隨內容增長線性膨脹），與按需載入原則衝突 |
| Orama | CJK 支援需額外 tokenizer 套件，生態成熟度低於 Pagefind |
| 不做搜尋，僅靠導航 | 知識庫的核心價值就是能被檢索，不可接受 |
